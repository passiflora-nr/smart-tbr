3 Moduł 3 — trzy skille jakości

Żaden nie zastępuje cyklu z modułu 2. Ustawiają kolejność, odwracają kolejność asercja/kod albo przenoszą test na przeglądarkę. Wszystkie trzy zapisują postęp w tym samym ## Progress.

/10x-test-plan
Warstwa orkiestracji. Mapa ryzyk, quality gates, fazy rolloutu. Czyta PRD, roadmapę, GIT churn i wywiad — nie linie w kodzie. Po każdej fazie dopisuje cookbook (§6).
→ test-plan.md
--status · --refresh
/10x-tdd
Ten sam plan.md, odwrócona kolejność: RED → GREEN → REFACTOR. Agent ujawnia asercję zanim napisze kod. Wymaga istniejącego runnera.
walidatory · kontrakty API · bugfix · regression guard
/10x-e2e
Pętla PLAN → GENERATE → REVIEW → VERIFY wobec działającej aplikacji. Seed test + 5 antywzorców. Jeśli ryzyko da się udowodnić funkcją — przekierowuje do TDD/implement.
getByRole · storageState · celowe psucie asercji
Mieszaj tryby w jednym planie: /10x-implement phase 1 (środowisko) → /10x-tdd phase 2 (kontrakt) → /10x-e2e phase 6 (ścieżka użytkownika). Reguła TDD: jeśli nie umiesz nazwać czerwonego testu jednym zdaniem — zostań przy implement albo wróć do researchu.

! Mapa ryzyk i problem wyroczni

Wpływ × prawdopodobieństwo

OcenaWpływPrawdopodobieństwo
Wysoki utrata dostępu, danych albo pieniędzy zmienia się co tydzień / już się tu przejechaliśmy
Średni funkcja działa gorzej, jest obejście kod ruszany od czasu do czasu
Niski kosmetyka, łatwo cofnąć kod stabilny, rzadko dotykany

Najpierw wysoki × wysoki. Awaria o ogromnym wpływie i znikomym prawdopodobieństwie (dostawca chmury) — obserwowalność, nie scenariusz testowy. Dorzuć osobno nadużycia: IDOR, injection, sekrety, rate-limit — agent sam ich nie zaproponuje.

Cost × signal · wyrocznia

Problem wyroczni. Test expect(fn()).toBe(0.15) odbija to, co kod robi, nie to, co powinien. Jeśli w funkcji siedzi błąd, test go zabetonuje. Oczekiwany wynik pochodzi z PRD / kontraktu / twojej wiedzy — nigdy z implementacji.
Sygnał, nie diagnoza /10x-test-plan mówi „ten obszar często się zmienia". Nie mówi „błąd jest w session.ts:42". Na plik patrzy dopiero research.
Cost × signal Najtańszy test, który łapie ryzyko. Nie e2e „bo bezpieczniej". Coverage przestaje być celem — celem jest sygnał dla konkretnego ryzyka.
Zielony to za mało Zepsuj chronione zachowanie. Jeśli test zostaje zielony, asercja niczego nie pilnuje. Stryker: żywy mutant = ślepa asercja. Nie goń mutation score do 100%.

☰ Pięć warstw jakości

Trzy warstwy lokalne + CI to pipeline proaktywny. Monitoring to siatka pod nim — łapie to, czego testy nie przewidziały. Menu, nie nakaz: zacznij od najlepszego cost × signal.

1. Per-edit
Hooki agenta po Write/Edit. Lint, szybki typecheck, vitest related $FILE. Jedyna warstwa, która karmi agenta w trakcie pracy.
Cursor: afterFileEdit
.cursor/hooks.json
2. Pre-commit
Hooki gitowe na staged files. Łapie ręczne edycje i checki zbyt wolne na per-edit. Husky / Lefthook / pre-commit.
lint + related tests
3. Pre-push
Cięższe sprawdzenia przed remote: pełny typecheck, szerszy zestaw testów, e2e na krytycznych flow.
minuty, nie milisekundy
4. CI
Ostatnia siatka przed współdzielonym stanem. Integracja, infrastruktura niedostępna lokalnie. Nie zastępuje warstw lokalnych.
każdy PR
5. Monitoring
Sentry / logi runtime. Jedyny stały sygnał dla połkniętych błędów (200 OK, efekt uboczny pada po cichu). Reaktywna strona tej samej dyscypliny.
produkcja · Sentry MCP

Hook: trigger → matcher → handler → sygnał

Exit codeZnaczenie
0sukces — kontynuuj
2błąd blokujący — agent widzi stdout i powinien naprawić
innylogowany, nie przerywa pracy

Heurystyka: check > kilka sekund → wyższa warstwa. Cursor: .cursor/hooks.json · Claude: .claude/settings.json (PostToolUse, matcher Write|Edit). Vitest 4.1+: AI_AGENT=1 — kompaktowe wyjście. Hooki są deterministyczne: przetrwają kompresję kontekstu, której CLAUDE.md nie przetrwa.

✕ Antywzorce testów od agenta

Unity — 3 klasy

Mirror implementacji Test sprawdza prywatny szczegół albo wynik policzony tą samą logiką co kod.
→ asercja na obserwowalny wynik scenariusza biznesowego
Tylko happy path Łatwe testy na poprawnych danych.
→ przynajmniej jeden edge case wynikający z ryzyka
Brak przypadków brzegowych Zero nulla, pustych danych, błędu środowiska.
→ test łapie to, co realnie uszkodzi użytkownika

E2E — 5 antywzorców

1. Naiwna asercja Sprawdza tytuł strony zamiast, czy fiszka przetrwała reload.
→ czy asercja padnie, gdy ryzyko się zmaterializuje?
2. Kruchy selektor div:nth-child(3) > button
→ getByRole('button', { name: 'Delete' })
3. Współdzielony stan Test B zakłada, że A utworzył deck. Flaky przy równoległym runie.
→ pełny setup + cleanup w jednym teście
4. waitForTimeout Czeka 3 s zamiast na stan. Pada w CI.
→ waitForResponse / expect().toBeVisible()
5. Brak cleanup Drugi przebieg: unique constraint violation.
→ Date.now() w ID + afterEach / afterAll

Re-prompt E2E: wskaż antywzorzec po nazwie, dlaczego nie chroni ryzyka, i wzorzec docelowy. Nie mów „popraw ten test". Seed test (seed.spec.ts) jest dźwignią: co pokażesz, to dostaniesz. Playwright CLI (~27K tokenów) przed MCP (~114K), chyba że sesja jest tylko do przeglądarki. Vision — suplement layoutu, nie default. Healer naprawia selektory; na zmianie logiki biznesowej maskuje buga.

⚡ Debug — od ticketa do fixa

Proaktywne testy łapią ryzyka, które potrafisz przewidzieć. Produkcja ujawnia resztę. Struktura dochodzenia jest stała — zmienia się tylko narzędzie (Sentry / Datadog, wrangler / vercel logs, Playwright / Cypress).

/10x-tdd lub /10x-e2eTest-driven bugfixing: padający test na trwały stan, potem minimalny fix. Test zostaje jako regression guard
Połknięty błąd (swallowed error). Handler loguje warn i zwraca 200 z wartością z pamięci. Użytkownik widzi sukces, trwały zapis przepadł. OWASP A10:2025. Hooki i typecheck tego nie złapią — TypeScript jest poprawny, pada zawartość w runtime. Stałym sygnałem jest monitoring. Fix ma dwie części: przestań połykać (500 zamiast 200) i napraw zapis. Weryfikacja jest lustrzanym odbiciem dochodzenia: każde źródło, które pokazało problem, musi potwierdzić, że go nie ma.
